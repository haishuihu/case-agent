三种方案对比

多模型兼容 · 聚焦核心生成链路 · 生产级目标

方案 A：指令精炼 + Few-Shot 增强

增量优化，不动架构

做什么

  • 收窄 SYSTEM_PROMPT 角色定义，降低认知负荷
  • 每个 Phase 补充 2-3 个精选 Few-Shot 示例
  • 添加输出质量自检清单到 prompt
  • 保持现有 .py 文件格式不变

代价

  • Phase 间仍共享 system prompt，聚焦问题治标不治本
  • 无版本追踪，改 prompt 靠 git diff 看
  • Few-Shot 示例硬编码，不同需求用同样的示例
  • 长期维护成本高

⭐ 方案 B：模块化 Prompt 系统 + CoT 引导

结构化重构，推荐方案

做什么

  • 每个 Phase 独立 System Prompt，精准聚焦
  • 引入 CoT 思维链模板（分析 → 设计 → 生成 → 校验）
  • Prompt 模板化（YAML/Markdown），与代码解耦
  • Prompt 版本管理器 + 评估套件
  • 多模型适配层（不同模型不同的 prompt 格式）

代价

  • 需重构生成管线（~3-5 天）
  • 需建立评估数据集和指标
  • 模板系统引入少量抽象层

方案 C：全链路 Prompt 平台

企业级基础设施

做什么

  • Prompt CMS（数据库存储 + UI 编辑器）
  • A/B 测试框架 + 自动化评估 pipeline
  • 动态 Few-Shot 检索（RAG for examples）
  • 输出护栏层（schema validation, auto-fix）

代价

  • 过度工程化，当前阶段 ROI 低
  • 前端+后端大量开发（~2-3 周）
  • 维护成本高，团队规模不匹配

方案 B 的核心设计

prompts/ 目录重构
├── templates/ ← YAML 模板文件（人类可读可编辑）
│ ├── phase1_requirement_review.yaml
│ ├── phase2_batch_generation.yaml
│ ├── phase3_smoke.yaml
│ ├── phase4_module_detail.yaml
│ └── phase5_review.yaml
├── examples/ ← Few-Shot 精选示例库
│ ├── smoke_examples.json
│ └── detail_examples.json
├── schemas/ ← 输出 JSON Schema
├── manager.py ← PromptManager（加载、版本、渲染）
└── evaluator.py ← 评估套件（evaluation harness）
保持向后兼容，现有 build_xxx_prompt() 函数保留为 adapter 层
