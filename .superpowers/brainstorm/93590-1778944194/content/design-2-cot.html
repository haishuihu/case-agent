设计二：CoT 思维链引导框架

用结构化思考步骤替代「凭感觉生成」，解决思考太宽泛和质量不稳定

核心机制：在 User Prompt 中嵌入思考模板

System Prompt 定义「你是谁」，CoT 模板定义「你怎么想」。
每个 Phase 有自己的思考链条，用 XML 标签框定思考空间。

以 Phase4 模块详情生成为例

User Prompt 结构（发给模型的实际内容）
## 任务上下文
需求: {requirement_text}
模块: M01 用户登录
子功能: 账号密码登录, 验证码登录, 忘记密码
业务规则: ...
数据约束: ...
已有用例: 12条 (P0/P1)

## 思考步骤（请严格按顺序执行）

<thinking>

<step name="功能理解">
1. 这个模块做什么？用户如何与之交互？
2. 列出所有输入字段和用户操作入口
3. 识别关键状态和状态转换
</step>

<step name="维度映射">
对每个覆盖维度，判断是否适用于本模块：
- 正常流程: [适用/不适用，原因]
- 边界值: [适用/不适用，原因]
- 异常处理: [适用/不适用，原因]
- ... (共10个维度)
</step>

<step name="测试点识别">
基于适用维度，列出所有需要测试的具体场景点：
- 正常流程: 场景A, 场景B, 场景C...
- 边界值: 场景D, 场景E...
- 注意：需要穷尽但不要重复
</step>

<step name="用例设计">
为每个测试点设计用例：
- 标题简洁描述测试意图
- 步骤可独立执行
- 预期结果可观测可验证
- 不确定的地方用「待确认」标注
</step>

<step name="自检">
1. 是否覆盖了所有适用的维度？
2. 是否有与已有用例重复的？
3. 用例数是否达到最低要求？
4. 每条用例是否可独立执行？
</step>

</thinking>

## 输出要求
基于以上思考，只输出 JSON：
{...}

为什么这样设计？

XML 标签框定思考空间

用 <thinking> 标签包裹思考过程，模型在标签内自由推理，输出时只取标签外的 JSON。避免思考内容污染输出格式。

维度适用性判断

不是所有10个维度都适用于每个模块。让模型先判断「哪些维度相关」，再聚焦精力在相关维度上深挖。解决「面面俱到但都不深入」的问题。

自检步骤内化质量控制

生成完后强制自检：覆盖完整？无重复？可执行？把质量把关从「靠运气」变成「靠流程」。
